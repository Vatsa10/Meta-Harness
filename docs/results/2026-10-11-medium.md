## Data and scale

`python -m meta_harness fetch symptom2disease --dir .meta-harness-data/cache` (160 train, 40 val,
200 test). Split with `random.Random(0)`: shuffle train and take 60 for **train**. Pool the other
100 train rows with the 40 val rows, shuffle, and take 100 for **search**. Shuffle test and take
100 for **test**. The splits share no input text. The search split has 21 labels and the test
split 22.

Each arm: 2 seeds (zero-shot, few-shot), 5 iterations of 2 proposals, `--max-evaluations 12`,
the default proposer cap of 40 tool calls, `--protocol online`.

## Command

```bash
python -m meta_harness --env-file <repo>/.env search \
  --harness baselines/classification/zero_shot.py --harness baselines/classification/few_shot.py \
  --train .meta-harness-data/s2d-med/train.jsonl --search .meta-harness-data/s2d-med/search.jsonl \
  --test .meta-harness-data/s2d-med/test.jsonl --protocol online \
  --domain classification --metric accuracy \
  --provider openai --model gpt-4o-mini --proposer-provider openai --proposer-model gpt-4.1-mini \
  --iterations 5 --candidates 2 --max-evaluations 12 --isolation process \
  --optimizer <metaharness|best-of-n> --seed <0|1> \
  --price openai:gpt-4o-mini=0.15,0.60,0.075 --price openai:gpt-4.1-mini=0.40,1.60,0.10 \
  --root .meta-harness-med-<arm>-s<seed>
```

## Why Best-of-N wrote nothing, and the fixes

The Best-of-N arm uses the `seed` view. It holds only `harness.py` and `scores.json` for the
`initial-*` candidates. The proposer log for seed 0 iteration 1, candidate 01, shows 40 calls of
`list`, `read` and `grep` and no write. Most of them grep `traces.jsonl` for `reward`,
`prediction`, `label` and so on. That file is not in the view, but `grep` on a missing path
answered `(no matches)`, which looks like a success. The prompt's layout also lists
`traces.jsonl` and tells the proposer to grep it. So the proposer kept searching for evidence it
could never get.

There was a second, separate loss. Some Best-of-N iterations did write `candidate-00.py`. But
when `candidate-01` then ran out of budget, the exception escaped `AgentProposer.__call__` and the
runner dropped the whole iteration, including the candidate already written.

Commits:

- `de4c943` fix(proposer): `grep` on a missing path is an error. The prompt now has a `{view_note}`
  that says which files exist in the `full`, `scores`, `summary` and `seed` views. With
  `max(3, cap // 5)` calls left, the proposer is reminded once to call `write_candidate`. Tests:
  `test_grep_on_a_missing_path_is_an_error_not_no_matches`,
  `test_seed_view_prompt_says_traces_are_absent`,
  `test_proposer_is_told_to_write_before_the_budget_runs_out` (scripted provider).
- `f9bc247` fix(proposer): a sibling proposal that gives up (budget, stuck or truncated) is
  recorded as `candidate-NN.error`. Candidates already written are kept, and the iteration raises
  only if every proposal failed. Test: `test_a_failed_sibling_proposal_keeps_the_written_candidate`
  (it fails on the old code).
- `a20bc0e` fix(providers): a 429 whose body says `insufficient_quota`,
  `credit_balance_exhausted` or `insufficient_user_quota` raises `QUOTA_EXHAUSTED` at once. Before,
  it was retried like throttling, so a run with no credits crawled through every call's retries.
  The killed test evaluation below hung for over 10 minutes this way. Test:
  `test_429_out_of_credits_is_not_retried`.

`python -m pytest -q tests`: 690 passed, 4 skipped.

## Can groq finish it? No

By this point unikey had no quota and OpenAI had no credits, so groq was the only provider left.
Its account is capped at 8,000 tokens per minute. A cap that low rejects any single request
larger than about 8k tokens.

- Probe with `openai/gpt-oss-120b`: a 6,079-token prompt succeeded. A prompt of about 10k tokens
  returned `HTTP 413 Request too large`.
- The proposer's conversation grows with each tool result. In the finished Meta-Harness seed-0
  run it averaged about 8.3k input tokens per call (925,739 over 111 calls), and the later turns
  of each proposal are larger than that. So proposer turns would hit 413 no matter how small the
  dataset is. Shrinking the split reduces the base-model load but not the proposer context.
- Throughput rules it out as well: about 0.9M proposer tokens per arm at 8k tokens a minute is
  about 2 hours per arm, before any base-model calls.

Shrinking the split does not make the design run on groq, so I did not run a smaller version.
Finishing the comparison needs either funded OpenAI or unikey credits, or a groq tier with a
higher token-per-minute limit.

## Conclusion

On the one finished seed, Meta-Harness's selected candidate scored 0.61 on the 100-example test
split against 0.53 for Best-of-N's selection (exact McNemar p = 0.039, 10 wins and 2 losses). The
result is significant at 0.05, but it is not evidence that the full experience view beats
Best-of-N. In that run Best-of-N proposed nothing because of two engine bugs, so its selection
was just the zero-shot seed. After the bugs were fixed, Best-of-N found candidates as good as
Meta-Harness's on the search split (0.65 to 0.66, against 0.58 to 0.74). We have no held-out test
numbers for the fixed runs. A fair answer needs the fixed seed-0 and seed-1 pairs rerun to
completion with funded credits. Another option is a single cheaper base model, such as groq
`openai/gpt-oss-20b`, used for both arms.
