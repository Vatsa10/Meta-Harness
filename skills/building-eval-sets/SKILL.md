# Building eval sets

## Overview

You cannot improve what you cannot score. An eval set is the smallest set of cases that turns
"seems better" into a number.

**Core principle:** 25 cases you actually have beat 500 you plan to collect.

## When to Use

- Someone reports an LLM feature is wrong, with examples
- You are about to edit a prompt that ships
- You want to compare two approaches and have no basis to choose

**Skip when:** the artifact is a throwaway script, or a human eyeballs every output anyway.

## The shape

One JSON object per line, one line per case:

```jsonl
{"input": "My card was charged twice for the same order.", "label": "duplicate_charge"}
{"input": "Charts render blank on Safari but fine on Chrome.", "label": "ui_bug"}
```

Fields by task type:

| Task | Required | Metric |
|---|---|---|
| Classification | `input`, `label` | exact match on the label |
| Extraction / QA | `input`, `answer` | normalized string or numeric match |
| Agent / code task | `instruction`, `test_command` | the command's exit code |

## Rules that make the number trustworthy

**Every reported failure goes in.** The tickets support forwarded are the most valuable cases you
have — they are the distribution you are actually failing on. Add them first, then fill out the
rest so they are not the whole set.

**Cover each class at least twice.** One case per label measures luck. With 12 labels, 25-40 cases
is the working range.

**Label from the ground truth, not the model.** If you generate labels by asking a model, you are
measuring agreement with that model, not correctness. Where the truth lives — a resolved ticket's
final queue, a merged PR, a support agent's correction — use that.

**Split before you tune.** Hold back ~30% and do not look at it until you are finished. See
`optimizing-harnesses` for why this is not optional.

**Make the metric mechanical.** Exact match, a regex, a numeric comparison, a test command's exit
code. If scoring requires judgment, you will drift toward scoring generously on the run you want
to win. When judgment is genuinely required, write the rubric down first and apply it blind.

## Getting to 25 cases in ten minutes

1. Paste in every reported failure. (Usually 3-10.)
2. Pull recent real inputs from logs, the ticket queue, or the database — whatever the feature
   consumes in production. Take them consecutively, not cherry-picked.
3. Label them from the resolved outcome, not from what the model says.
4. Check class coverage; add cases for any class with fewer than two.

Synthetic cases are a last resort and belong flagged as such: a model writing its own test set
writes cases it already passes.

## Common Mistakes

| Mistake | Why it burns you |
|---|---|
| Only the reported failures | You optimize for six tickets and regress everything else |
| Labels generated by the model under test | Measures self-consistency, not accuracy |
| Cases hand-picked as "representative" | Selection bias; take consecutive real inputs |
| No held-out split | The number you report is the number you tuned against |
| Metric involving "does this look right" | Scoring drifts toward whichever run you want to win |

## Real-World Impact

A 36-case set built this way separated four harness baselines from each other on the first run —
two scored 1.00, two scored 0.96 — and the held-out split came back at 0.82, which was the honest
number and 18 points below what the tuning split claimed.
